# CarbonTracer token + Excel + QR demo

Standalone Django API and browser frontend. Creating a token automatically produces a workbook and a PNG QR code. The workbook uses all ten sheets of the supplied CarbonTracer sample, preserving its layout and measurements. Each token has its own workbook rather than one row in a shared workbook, because the supplied format describes one complete token.

## Run on Windows

From this folder:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8010 --insecure
```

Open http://127.0.0.1:8010/. `--insecure` only enables Django's development static-file server with DEBUG=False; this is a local demo command, not a production server configuration.

1. Enter a unique token number, project and facility.
2. Click **Create token & generate QR**.
3. Open the token: its QR destination is the Excel workbook itself. Scanning it opens/downloads the complete `.xlsx` report.
4. The optional browser report remains available from the management link, but it is not encoded in the QR.
5. From the home page, choose **Edit demo status** to access the separate management screen. Change **Demo verification status**, save, and reopen the same QR link to see the updated report. Downloads remain available on the creation/management screens.

Other values, including process dates, measurements, calculated-looking figures, review labels and evidence references, remain the source's synthetic sample data. The app does not recalculate or certify carbon removal. Evidence references are shown as text; their files were not supplied.

## Files

| Location | Contents |
|---|---|
| `fixtures/carbontracer-template.xlsx` | Exact copy of the supplied format; original in Downloads is untouched |
| `data/registry.sqlite3` | Stable UUID, token number, original inputs, request ID, state and permanent QR URL |
| `data/tokens/<uuid>/workbook.xlsx` | One workbook per token |
| `data/tokens/<uuid>/qr.png` | QR generated by Django |

The public UUID maps to the workbook using the registry. The business token number replaces the source token number throughout the workbook. Only project, facility, token identity and demo summary status are edited during creation. Other source content/styles remain unchanged.

Downloading Excel creates a snapshot. Editing the downloaded snapshot does not update the server. For this local demo, edit the actual workbook under `data/tokens/<uuid>/workbook.xlsx` and save/close it, then reload the record. Do not edit the template to update an existing token. Manual Excel editing should happen while no API writes are in progress; Excel does not honor the app's file lock. An upload/import workflow is not included.

## API

| Method | URL | Purpose |
|---|---|---|
| GET | `/api/tokens/` | Latest 100 ready tokens |
| POST | `/api/tokens/` | Create workbook and QR |
| GET | `/api/tokens/<uuid>/` | Read latest workbook, all sheets |
| PATCH | `/api/tokens/<uuid>/` | Update demo verification status |
| GET | `/api/tokens/<uuid>/qr.png` | QR PNG |
| GET | `/api/tokens/<uuid>/workbook.xlsx` | Workbook download |
| GET | `/tokens/<uuid>/` | Optional read-only browser report |
| GET | `/tokens/<uuid>/manage/` | Separate demo management screen |

Create body:

```json
{"request_id":"46c4fa62-6f3f-45b6-8bb3-c2ce926d8fe5","token_number":"DEMO-001","project":"Sample project","facility":"Sample facility"}
```

Create returns 201 (or 200 for an identical completed retry), `id`, `qr_url`, relative `qr_image_url`, relative `workbook_url`, `summary` and `sheets`. Clients resolve relative image/download paths against the API origin. Reuse the same request_id and body on a failed network request. A changed body with an existing request ID or duplicate token number returns 409. Invalid input returns 400; inaccessible files return 503. Browser writes require the CSRF cookie and `X-CSRFToken`, obtained by first opening `/`. No CSRF exemptions are used.

PATCH body:

```json
{"verification_status":"IN REVIEW - DEMO"}
```

Supported states: `DRAFT - DEMO`, `IN REVIEW - DEMO`, `COMPLETE - DEMO`. This only changes the summary, not the original sample review evidence.

## Failure handling

Creation registers a PENDING token before writing files, then writes Excel and QR through temporary files + atomic replacement, then marks READY. A failed step can resume with the same request ID. Incomplete tokens are not exposed as ready. Writes are serialized across processes through a file lock on the same disk. Excel and image operations are not part of a database transaction. This design is for one host with one persistent local filesystem, not a distributed storage cluster.

## Scanning from a phone

Loopback URLs cannot be reached from another device. Before creating phone-test tokens, configure your computer's LAN address (replace the example):

```powershell
$env:PUBLIC_BASE_URL = 'http://192.168.1.50:8010'
$env:ALLOWED_HOSTS = '127.0.0.1,localhost,192.168.1.50'
.venv\Scripts\python.exe manage.py runserver 0.0.0.0:8010 --insecure
```

Use the same Wi-Fi and permit the port through your firewall. The phone's camera opens the QR's web page. Existing QR URLs remain fixed; changing PUBLIC_BASE_URL affects newly created tokens only. The app also accepts a pasted same-origin QR link/UUID. In-browser camera scanning is not included.

## Before production

This intentionally anonymous local demo contains only sample data. Add authentication, per-facility authorization on every record/file, a production server and static setup, HTTPS, a secret key, backups and persistent storage. Mount `TOKEN_DATA_ROOT` on a persistent volume; default storage is `data/`. Adopt a database-backed authoritative business model for concurrent production operations. Do not expose this demo unchanged to the public internet.
